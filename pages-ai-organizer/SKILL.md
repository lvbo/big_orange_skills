# pages-ai 自动归类

把 `pages-ai/` 根目录视为待整理入口。每次运行都根据当前三个总览文件的真实结构重新判断，不把某次分类结果硬编码成永久规则。

## 固定范围

- 只处理 `pages-ai/` 根目录直接包含的 `*.md`，包括 `*.excalidraw.md`；不要递归处理已经归类的文件。
- 读取并更新且仅更新以下三个总览：
  - `pages-ai/01-projects/01-Projects(项目).md`
  - `pages-ai/02-areas/02-Areas(领域).md`
  - `pages-ai/03-resources/03-Resources(资源).md`
- 目标目录分别为 `pages-ai/01-projects/`、`pages-ai/02-areas/`、`pages-ai/03-resources/`。
- 不处理 `raw/`、`wiki/`、`outputs/`、`journals*/` 或 `pages-ai/04-archives/`。Archives 代表用户明确结束或封存的内容，不能仅凭“看起来较旧”自动归档。
- 不修改候选笔记正文、frontmatter、文件名和扩展名；本任务只调整总览关系和文件位置。

## PARA 判断

先读正文再分类，标题只能作为线索。结合 frontmatter、标题层级、任务/日期、正文语义、出链，以及三个总览中相邻条目的语境作判断。

1. **Projects**：有明确期望结果、阶段目标或交付物，通常会完成或结束。例如冲高专项、系统改造、一次性研究或实施计划。仅仅提到某个项目，不足以把参考资料归为 Project。
2. **Areas**：需要持续负责、维护或达到标准的长期领域，没有自然结束点。例如健康、家庭、团队管理、长期运维、业务领域和个人档案。
3. **Resources**：供未来查阅或学习的主题资料。例如概念、方法、工具说明、书籍/文章笔记、技术手册、品牌清单和经验知识。

冲突时看笔记的主要用途：推动当前结果优先归 Project；承载持续责任优先归 Area；解释“是什么/怎么做”、以复用查阅为主则归 Resource。每篇笔记只能有一个主归属和一个目标目录，但正文已有的其他相关链接可以保留。

## 工作流

### 1. 定位 Vault 并盘点

1. 确认当前目录或已知工作区是包含 `pages-ai/` 的 Vault 根目录。
2. 从本 Skill 目录运行只读审计：

```bash
python3 scripts/audit_pages_ai.py --vault "/absolute/path/to/vault" --json
```

3. 若三个总览任一缺失，停止写入并报告缺失路径。若没有根目录候选，直接报告“没有待归类笔记”，不要改文件。
4. 记录三个总览和候选文件的原始状态，以便写后确认没有漏项或覆盖。

### 2. 建立当前分类图

完整读取三个总览，提取标题层级、列表缩进、已有 WikiLink 和相邻主题。总览可能很长，应按候选主题用 `rg` 检索相关词，并读取命中点前后的完整小节；仍无法判断时再扩大范围。

对每个候选生成内部计划，至少包含：

- 原路径与不含扩展名的链接标题；
- Projects / Areas / Resources 判断及一条基于正文的理由；
- 目标总览中的具体标题路径，例如 `技术工程 > AI`；
- 目标文件路径；
- 当前是否已经被一个或多个总览链接。

不要在计划完成前移动任何文件。

### 3. 处理冲突

- 若目标目录已有同名文件，比较内容：内容相同则保留已有目标，不覆盖，候选留在原处并列为“需人工确认”；内容不同也不覆盖、不改名，候选留在原处并报告冲突。
- 若候选已在正确总览的正确层级出现，只移动文件，不重复加链接。
- 若候选只在错误总览出现，将该条 WikiLink 从错误总览移到正确总览；不要留下多个主归属。
- 若同一候选在多个总览出现，依据正文确定唯一主归属，删除其他两个总览中仅用于主分类的重复列表项。若某处链接嵌在带有用户说明的复杂段落中，不能安全拆除时停止该项并报告，而不是破坏原文。

### 4. 更新总览

在目标标题的对应列表中插入 `- [[笔记名]]`，复用该小节现有缩进、排序和空行风格。

- 优先选择现有的最具体标题或父 WikiLink；如果父条目本身是 WikiLink 且已有子列表，把新条目作为同级子项。
- 只有当至少三篇本批笔记形成稳定且明显缺失的共同主题时，才新建小标题；否则放入最接近的现有小节，无法更具体时使用该总览已有的“未分组”。
- 内部笔记使用 WikiLink，不写 Vault 绝对路径；不要把同一链接重复追加。
- 采用精确补丁，保留无关条目、缩进、外部链接、标签、批注和 frontmatter。

### 5. 移动文件

总览补丁准备完成后再逐项移动。优先使用当前 Obsidian CLI 帮助中提供的 `move` 命令，因为 Obsidian 能同步更新受影响链接；运行前用 `obsidian help` 确认本机版本的确切参数。若 Obsidian CLI 不可用，才使用文件系统移动，并在汇总中说明该降级方式及相对 Markdown 链接可能需要复核。

一次只移动计划中无冲突的明确项目。某一项失败不应导致其余项被错误报告为成功；保留失败项原文件并继续验证已完成项。

### 6. 写后验证

重新运行审计脚本并复读受影响的总览，逐项确认：

- 每个成功项的原路径已不存在，目标路径存在且内容未改变；
- 每个成功项恰好出现在一个 PARA 总览中，且位于计划的小节；
- 未成功项仍在原路径，且没有新增误导性链接；
- 没有覆盖同名文件，没有重复 WikiLink，没有改动候选正文；
- 本轮开始时发现的每个候选都出现在“已移动”或“未移动”清单中。

验证失败时修正可安全修正的问题；无法修正则明确列为失败，不声称全部完成。

## 完成汇报

使用下面的紧凑格式，让用户能从结果追溯每一次移动：

```markdown
# pages-ai 自动归类结果

- 扫描：N 篇
- 已移动：N 篇
- 未移动：N 篇

| 原文件 | PARA 主归属 | 总览位置 | 目标文件 | 判断依据 |
|---|---|---|---|---|
| pages-ai/示例.md | Resources | 技术工程 > AI | pages-ai/03-resources/示例.md | 正文是可复用的工具说明 |

## 未移动与需确认

- 无；或列出冲突、失败和保留原路径。

## 验证

- 总览链接、目标文件、原路径和重复项检查结果。
```

若使用了文件系统移动降级，在“验证”中明确说明。
