# 增量同步当日计划

这是 Calendar + Things 写入当日日记的唯一实现。采用保守的增量合并：已有日记内容代表用户整理过的工作现场，不重建计划，不用外部数据覆盖手工编辑。

## 数据范围

### Apple Calendar

- 用本机 `date` 得到本地时区的 `[今日 00:00, 明日 00:00)`，查询“工作”“个人”“吕波”三个日历。
- `accli calendars`、`accli events` 直接在非沙箱环境运行，用户已授权，无需确认。若仍返回 `NOT_AUTHORIZED`，报告 macOS 日历权限问题。
- 优先读取 JSON 的 `summary`、`location`、`allDay`、`start`、`end`，并保留来源查询顺序“工作”“个人”“吕波”。
- 纳入与当天区间有重叠的定时事件以及当天的全天事件。跨日事件显示源数据的本地起止时分，计算容量时只计与当天区间重叠的部分。

### Things

- 运行 `things today --format json --select uuid,title,status,today_index`，或按 `things` Skill 的等价只读方式获取数据。
- 使用默认状态过滤，只同步 Today 中当前未完成的待办；不使用 `--status any` 或 `--all`。
- 保持 Today 返回顺序，只写 `title`，不写 UUID、项目、区域或标签；不修改 Things。

任一来源失败时，不用缓存或猜测结果代替。可以安全合并成功来源，但必须报告失败来源；由于容量可能不完整，不应把最终结果称为“完整同步”。

## 写入目标与缺失结构

1. 目标文件为 `journals/YYYY-MM-DD.md`。先读完整文件。
2. 文件不存在时停止，建议先运行 `obsidian-morning-daily-note` 或 `start-today`；本 Skill 不创建整篇日记。
3. `### 每日计划` 不存在时，可在以下条件全部满足时补建一个空章节：文件可解析、能找到合适的同级章节边界，且插入不会拆开 frontmatter、代码块或现有章节。优先放在 `### 每日投入` 之前；否则放在最后一个同级日常记录章节之后。无法确定安全位置时停止并报告，不重建日记。
4. `### 每日投入` 不存在时，按同样的安全条件在“每日计划”之后补建；无法安全补建时仍可同步“每日计划”，但跳过容量提醒并明确报告。

## 格式

定时日程写入“会议”节点下，缩进一个 Tab：

```markdown
- 会议
	- [HH:mm～HH:mm] 日程名称 日程地点 [时间花费]
```

- 地点为空时省略；时间花费用 `30分钟`、`1小时`、`1小时30分钟`。
- 全天日程写为 `- [全天] 日程名称 日程地点`，不虚构时间或时长；容量按 0 分钟计算。
- 本轮缺失的定时日程按开始时间排序，同一时间按日历查询顺序稳定排序；全天日程排在本轮定时日程之前。为了保护原文，不承诺重排已有日程，因此整个历史列表未必全局有序。

Things 待办是“每日计划”的直接子项，位于完整“会议”节点之后：

```markdown
- 待办标题
```

不自动添加 `TODO`、复选框、UUID、来源标签或工时标记。

## 增量合并

### 保护边界

- 不删除、重排或改写已有条目，不改变状态、缩进、标记、块 ID、链接、批注或用户工时。
- 只允许修改 `### 每日计划`、`### 每日投入` 中带固定签名的容量提醒块、按兼容规则唯一识别的旧版精确提醒，以及按“缺失结构”规则安全补建的两个标题和空章节；除此以外的原文必须保持不变。
- 两个章节均结束于下一个同级或更高级 Markdown 标题，或文件末尾。识别标题时忽略代码块内文本。

### 判重

- 日历：在“会议”现有子项中按“全天标志或起止时间 + 完整日程名称”精确判断；比较前仅忽略项目符号、缩进和 `DONE`/`TODO`/复选框等状态前缀，允许末尾已有地点、时长、标签或批注。不要只按模糊关键词匹配。
- Things：在“每日计划”的直接子项中按完整标题精确判断；可忽略项目符号、状态前缀、首尾空白、块 ID，以及标题后的明确状态/投入标记。不要把“会议”节点或其子项当 Things 待办。
- 疑似改期或改名时保留旧条目，把当前版本作为新条目，并在报告中提示。

### 插入位置

1. “会议”节点存在时，把本轮缺失日程按上述本轮顺序追加到其最后一个子项之后；不存在时在“每日计划”开头创建。
2. 把本轮缺失 Things 按 Today 顺序追加到已有直接待办之后。不要把新待办插到旧待办之前；这样多轮同步仍保持已有顺序。
3. 如果存在无法归类的直接子项或用户说明文字，选择不会拆开其结构的最近安全位置；不确定时停止该部分写入并报告。
4. 没有新增项时不改“每日计划”，但仍执行容量检查。

## 计划容量检查

每次同步结束（包括 no-op）都根据当前 `### 每日计划` 重新计算：

- 日程：定时日程按起止时间计算；结束时分早于开始时分视为跨越零点。若本轮源数据可确认跨日范围，只计当天区间的重叠分钟。现有条目中的方括号时长仅用于展示，不覆盖起止时间。全天日程计 0 分钟，不把“全天”猜成 24 小时。
- 待办：在“会议”节点之外的任务条目中，每个 `🍅` 计 25 分钟，每个 `🍉` 计 15 分钟；`🥔`、`🍠` 是实际投入，不计入预估。无计划标记计 0，不猜测。
- 不统计“每日投入”或其他章节，也不把“会议”父节点和说明文字当任务。

总计严格大于 540 分钟时，在 `### 每日投入` 标题后的第一个可见内容位置维护以下受管块；整小时省略分钟：

```markdown
<!-- sync-today-plan:capacity-warning:start -->
- ⚠️ 今日计划预计投入 X小时Y分钟，超过 9 小时，计划的事情太多了。
<!-- sync-today-plan:capacity-warning:end -->
```

总计不大于 540 分钟时，删除整个受管块。只更新或删除这两个固定签名之间的内容；不得删除未带签名的相似提醒或任何用户文本。兼容旧版时，若“每日投入”标题后的第一个可见内容恰好只有一条符合完整旧格式 `- ⚠️ 今日计划预计投入 ...，超过 9 小时，计划的事情太多了。` 的无标记行，先把它视作可迁移的旧受管内容：当前总计大于 540 分钟时原位替换为带签名的新块，当前总计不大于 540 分钟时删除这一条唯一旧行。多个候选、位置不符或文字不完全匹配时保留并报告。若发现多个完整受管块，合并为标题后的一个；若签名残缺，停止修改提醒并报告，避免误删。

## 执行与验证

1. 读取三类日历、Things Today 和目标日记，在内存中计算缺失项。
2. 修改前保存原文，并确认每个补丁只落在允许区域；用精确补丁编辑，不整篇覆写。
3. 同步后重新读取文件、重新计算容量并维护提醒块，再次读取验证：
   - 每个新增项恰好出现一次，缩进和父节点正确；
   - 原有文本保持原顺序且未被改写；
   - 章节边界之外仅有受管提醒块、按兼容规则迁移或删除的唯一旧版精确提醒，或本次按规则补建的“每日计划/每日投入”标题与空章节发生预期变化；
   - 受管提醒块最多一个，数值与重新计算结果一致；总计不大于 9 小时时不存在完整受管块。
4. 任一验证失败时明确报告，不声称完整成功。

## 报告

报告目标文件、新增 Calendar/Things 数量和标题、跳过重复数量、章节补建情况、容量总计以及提醒是新增/更新/移除/无需提醒。另列疑似改期、来源失败、残缺签名或验证失败；无新增时说明“外部计划已同步，日记的每日计划未修改”，同时报告容量检查结果。
